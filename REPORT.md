# Отчет по лабораторной работе: AI Code-Review Бот в CI

## Архитектура и реализация
- Триггер: GitHub Actions workflow (`.github/workflows/ai-review.yml`), запускающийся при opened и synchronize пул-реквеста.
- Безопасность: Ключ модели хранится в GitHub Secrets (`POLZA_API_KEY`) и используется в workflow (`ai-review.yml`), права токена минимальны (`contents: read`, `pull-requests: write`).
- Фильтрация diff: Используется three-dot diff (`origin/base...head` в `ai-review.yml`), через команду исключаются lock-файлы (`*.lock`), папки сборки (`dist/`, `generated/`), а через парсинг в функции `parse_diff()` скрипта `review.py` исключаются бинарники.
- Ограничения размера: Ревью пропускается, если PR содержит более 30 изменённых файлов или более 1000 строк изменений. 
- Надежность (Fallback): Скрипт `review.py` проверяет валидность JSON ответа модели, сопоставляет номера строк с реальным diff (`valid_lines`). Если модель указывает несуществующую строку, замечание не падает с ошибкой 422 от GitHub API (в блоке публикации `ai-review.yml`), а переносится в общий summary.

##  Инстркуции

Бот проверяет код по фиксированному списку правил:
- Безопасность: SQL-инъекции (конкатенация/f-строки вместо параметров), захардкоженные секреты.
- Отсутствие обработки ожидаемых ошибок при выполнении сетевых и файловых операций.
- Логирование: Использование print() вместо штатного логгера.
- Бизнес-логика БД: Использование сырых строк статусов вместо констант ArtworkStatus.
- Тестирование: Наличие изменений в tests/ при добавлении новой функциональности.
- Отладка: Использование breakpoint() в рабочем коде.
## Расчет метрик качества (Precision / Recall)
- True Positives (TP): Реальные проблемы, которые бот успешно нашел и привязал к строкам.
- False Positives (FP): Выдуманные ботом проблемы или ложные срабатывания на корректный код (bait).
- False Negatives (FN): Реальные заложенные проблемы, которые бот пропустил.
Формулы:
- $\text{Precision} = \frac{TP}{TP + FP}$
- $\text{Recall} = \frac{TP}{TP + FN}$

## Выводы и анализ качества reviewer'а

В ходе эксперимента AI Code-Review бот был проверен на Pull Request с 13 заранее внесёнными дефектами, соответствующими правилам из файла `.github/review-instructions.md`.

**1. Полнота обнаружения проблем**

В последнем запуске бот обнаружил все 13 из 13 эталонных дефектов. Пропущенных проблем не осталось (FN = 0), поэтому полнота обнаружения (Recall) составила 100%.

Бот смог выявить нарушения нескольких типов:

- проблемы безопасности: небезопасное формирование SQL-запросов и захардкоженный ключ;
- проблемы обработки ошибок: отсутствие обработки исключений и подавление ошибок через `except: pass`;
- нарушения соглашений проекта: использование сырых строк статусов вместо `ArtworkStatus`;
- проблемы логирования и отладки: `print()` вместо логгера и оставленный `breakpoint()`;
- логические ошибки в аналитических запросах;
- добавление функциональности без соответствующего теста.

Это показывает, что reviewer способен проверять не только очевидные синтаксические и стилистические проблемы, но и некоторые нарушения логики приложения с учётом заданных инструкций.

**2. Ложные срабатывания**

В контрольном примере BAIT-1 бот не стал требовать фильтрацию по статусу `DONE` в функции `status_counts()`, поскольку эта функция должна учитывать все статусы.

Ложных срабатываний в проверенной выборке не обнаружено (FP = 0). Precision составила 100%.

Однако проверялся только один специально подготовленный контрольный пример. Поэтому отсутствие FP в данном эксперименте не означает, что бот не будет ошибочно комментировать корректный код в других проектах.

**3. Изменение качества после исправления**

В первом запуске бот обнаружил 12 из 13 дефектов (Recall = 92,31%). После анализа была выявлена и исправлена проблема в разборе Git diff, из-за которой часть замечаний не проходила проверку допустимых координат.

В повторном запуске были обнаружены все 13 дефектов. Таким образом, улучшение результата было достигнуто не за счёт изменения набора инструкций, а благодаря исправлению технической части reviewer'а — обработки diff и координат комментариев.

**4. Практическая применимость**

Помимо обнаружения проблем, бот успешно публикует замечания непосредственно в GitHub Pull Request, привязывая их к соответствующим строкам изменённого кода. Для части замечаний также формируются предложения исправлений (`suggestions`).

Проверка координат перед публикацией позволяет избежать отправки некорректных inline-комментариев. Если замечание нельзя привязать к существующей строке diff, оно переносится в общий summary.


**5. Ограничения эксперимента**

Полученные метрики нельзя рассматривать как объективную оценку качества reviewer'а на произвольном коде. Проверка проводилась:

- на одном специально подготовленном Pull Request;
- в рамках одного проекта;
- на 13 заранее известных дефектах, подобранных под фиксированный набор инструкций;
- с использованием только одного контрольного примера для проверки ложных срабатываний.

Кроме того, эксперимент не позволяет оценить качество обнаружения неизвестных типов ошибок, устойчивость к более сложным изменениям и поведение на больших реальных Pull Request.
